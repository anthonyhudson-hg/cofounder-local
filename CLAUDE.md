# Cofounder

Desktop app: React + TypeScript + Tauri (Rust) + SQLite. Slack-style UI with a `#general` channel and a `Chief of Staff` DM backed by a pluggable **agent provider** (Claude or Codex). A single Node.js **runtime** process — spawned automatically by the Rust backend and owning SQLite outright (via `better-sqlite3` + Kysely) — serves a typed Command/Query/Event/Delta protocol and owns the entire turn loop for both DMs and channels (full cutover from an earlier dual-process/client-orchestrated design; there is no other backend process). All config (system prompt, default model/effort) lives in the `settings` SQLite table, not in files.

## Runtime architecture

- **Protocol**: `shared/protocol.d.ts` defines `CommandEnvelope`/`QueryEnvelope`/`ResultEnvelope`/`DeltaEnvelope`/`EventEnvelope`, newline-delimited JSON over stdio. Rust (`src-tauri/src/sidecar.rs`) is a dumb, provider-agnostic transport: `send_to_runtime` forwards an opaque envelope to the runtime's stdin; every runtime stdout line is re-emitted to the webview as `runtime://event`. `src/lib/runtimeClient.ts` is the frontend's typed client (`command()`/`query()`/`commandStreaming()`), correlating replies by id and resetting a streaming call's idle timeout on every delta.
- **Domains**: `sidecar/src/domains/*/service.ts` hold the actual logic; `sidecar/src/domains/register.ts` wires each `command:*`/`query:*` type to its handler (imported for side effects by `sidecar/src/runtime/index.ts`). Every mutation goes through `runtime/unitOfWork.ts`'s `mutate()` — a single transaction plus an atomically-appended event, so DB state and the event log never diverge.
- **Turn loop**: `conversations/service.ts`'s `sendMessage()` (DM, `command:message.send`) and `sendChannelMessage()` (channel, `command:message.sendChannel`) both run entirely server-side — persisting the user message, composing the system prompt (identity/manager/mention-scope/reaction-notices), driving the provider, parsing the model's output, and persisting the result — with `sink.delta()` streaming assistant text back to the client mid-turn. Channel sends additionally relevance-gate every member (an `@mention` always bypasses the gate) and run each responder in parallel, parsing a `respondsWithText`/`replyToMessageId`/`threadRootId`/`reactions` control block out of each one's reply. The frontend hooks (`useConversation.ts`/`useChannel.ts`) are now thin optimistic-UI layers: they render a local placeholder immediately, stream deltas into it, and reconcile with the DB via `reload()` once the command resolves (the server generates the real ids, so reactions/thread-replies keyed by id need the authoritative row, not the client's placeholder).
- **Small pure helpers duplicated by necessity** (Node/browser split, no shared workspace package): `runtime/promptBuilder.ts`, `runtime/mentions.ts`, `runtime/reactionFormatting.ts`, and `runtime/models.ts` are intentional forks of `src/lib/promptBuilder.ts`, `src/lib/mentions.ts`, `src/lib/emoji.ts`'s reaction-intent map, and `src/types.ts`'s `MODELS[]` id→provider mapping, respectively. Keep both sides in sync by hand when changing any of them.

## Multi-provider architecture

Each employee's `default_model` picks both the model and, via the model registry, the **provider** (`src/types.ts` `MODELS[].provider` + `modelProvider()`; the runtime keeps its own copy in `runtime/models.ts`, see above). For a DM send the frontend still resolves and passes the provider explicitly (`command:message.send`'s payload); for a channel send the runtime resolves each member's provider itself from their stored `default_model`, since there's no client in that loop per-turn.

- **Sidecar provider seam:** `sidecar/src/providers/` — `AgentProvider.runTurn()` yields text chunks and returns `{sessionId, success, usage, totalCostUsd}`. `ClaudeProvider` wraps `@anthropic-ai/claude-agent-sdk`'s `query()`; `CodexProvider` wraps `@openai/codex-sdk`. `getProvider(name)` defaults to Claude.
- **Codex specifics:** the SDK is ESM-only, so it's loaded via a `new Function`-guarded dynamic `import()` to survive the CommonJS downlevel (`ClaudeProvider` uses the identical guard for the same reason — see Tech debt below). Codex has no system-prompt channel, so the persona is folded into each turn's input. Effort maps onto Codex's ladder (`max`→`high`). Codex reports no cost (`totalCostUsd: 0`); token counts are exact. Runs `sandboxMode: "read-only"`, `approvalPolicy: "never"` in `os.tmpdir()` since these agents are chat-only (no tools). **`@openai/codex-sdk` vendors and spawns its own platform-specific `codex` CLI binary** via a `require.resolve("@openai/codex/package.json")` → matching platform optional-dependency package → `child_process.spawn()` chain — it does **not** shell out to a system-installed `codex` on PATH (this was previously misdocumented here). Auth is still the user's local ChatGPT login (`codex login`) or `OPENAI_API_KEY`, same subscription shape as Claude Code; only the binary itself is bundled, not the auth.
- **Sessions are provider-owned.** `conversations.session_id`/`agent_sessions.session_id` are opaque handles that only resume with the provider that minted them. Both tables carry a `session_provider` column; a stored session is dropped (fresh thread instead of resume) whenever the selected provider differs from the one that minted it. The channel relevance check is always a cheap internal Claude call regardless of the employee's own chat provider.

## Packaging & updates (Windows)

The app ships as a Node-independent NSIS installer plus auto-updates — no system-installed Node is required on the target machine, and no separate `codex`/`claude` CLI install either (both provider SDKs vendor their own platform binaries, see above).

- **Bundling strategy: portable Node + resources, not a single-file compile.** An earlier plan to compile `sidecar/src/runtime/index.ts` into a standalone binary via `@yao-pkg/pkg` was abandoned after scoping found it unverified (no trace of pkg anywhere in the repo despite a prior note claiming it worked) and materially harder than expected — `better-sqlite3`, `@napi-rs/keyring`, and both provider SDKs each ship a platform-specific native/vendored binary that a static single-file compiler can't reliably embed. Instead: `scripts/fetch-node.mjs` downloads and SHA-256-verifies a portable `node.exe`, staged at `src-tauri/binaries/sidecar-node-x86_64-pc-windows-msvc.exe` and registered as a Tauri `externalBin` (`bundle.externalBin` in `tauri.conf.json`); `sidecar/dist` + `sidecar/node_modules` + `sidecar/package.json` ship as-is via `bundle.resources` (map syntax — the array form mangles `../` into a literal `_up_` path segment and breaks resolution). `sidecar.rs`'s `resolve_node_binary()` finds the bundled binary next to the main `.exe` (externalBin's placement, confirmed empirically — target-triple suffix stripped) and falls back to a system `node` on PATH only in dev, where no bundled binary exists.
- **Two real Windows-specific bugs were found and fixed getting this working, both non-obvious:** (1) `resource_dir()`/`app_config_dir()`/`current_exe()` can return a Windows extended-length "verbatim" path (`\\?\C:\...`) that Node's own module loader can't parse (`EISDIR: illegal operation on a directory, lstat 'C:'`), even though the path is otherwise valid — `sidecar.rs`'s `strip_verbatim_prefix()` strips it before handing any path to the Node process. (2) Node's ESM/CJS module-type detection walks up the directory tree for the nearest `package.json`; omitting `sidecar/package.json` (`type: commonjs`) from the bundled resources let it walk past the bundled tree and pick up the *root* project's `package.json` (`type: module`) instead, misinterpreting the whole runtime as an ES module — fixed by staging `sidecar/package.json` as its own resource.
- **`claude.ts`/`codex.ts` ESM-loading guard.** `providers/claude.ts` now uses the same `new Function("specifier","return import(specifier)")` dynamic-import guard `codex.ts` already had, rather than a plain static import that `tsc` downlevels to `require(...)` — that only "worked" because dev machines happen to run a Node new enough for unflagged `require(ESM)`; a bundled build's exact Node version (now pinned by `fetch-node.mjs`) shouldn't be a silent precondition for the Claude provider to function.
- **Installer branding**: NSIS header/sidebar images (`src-tauri/installer/*.bmp`, generated once via `scripts/generate-installer-assets.py`, output committed) built from the app's own icon composited onto its actual theme gradients (`src/App.css`'s `--sidebar-bg`/`--titlebar-bg`), not Tauri's stock default chrome. `installMode: currentUser` avoids requiring admin elevation to install.
- **Auto-updates**: `tauri-plugin-updater` + `tauri-plugin-process`, checked once on app launch (`src/hooks/useUpdateChecker.ts`) with a dismissible in-app banner plus a manual "Check for updates" button in company settings. Update artifacts are hosted as GitHub Releases on the (public) `anthonyhudson-hg/cofounder-local` repo — see `RELEASING.md` for the full cut-a-release process, including why `bundle.targets` is scoped to `["nsis"]` only (the updater doesn't support MSI on Windows, and WiX packaging of this resource tree was dramatically slower for an artifact that would never ship).
- **Packaging is slow, not broken.** `sidecar/node_modules` (several hundred MB after pruning devDependencies, mostly the vendored Claude/Codex CLI binaries) takes NSIS a long time (15+ minutes observed) to LZMA-compress into the installer. This is a real cost of the "ship node_modules as-is" strategy, not a hang — see `RELEASING.md` for what a normal build looks like.
- **Not yet run: a genuinely clean-machine test via Windows Sandbox.** Every verification so far was "strip `node` from this dev machine's PATH and launch" (repeated, reliable, passing) — a true clean-image test needs an elevated one-time setup step (`Windows Sandbox` optional feature) that wasn't done as part of this work. Worth doing once before handing a build to an actual design partner.

## Other tech debt

- **`total_cost_usd` is a client-side estimate, not real billing.** The Claude Agent SDK computes it from a bundled local price table regardless of auth method (API key vs. Claude subscription/OAuth), and that table may not yet have accurate pricing for newest models. Treat the "~$X est." figure shown per-message as directional only, not authoritative — token counts (input/output/cache) are the reliable numbers.
